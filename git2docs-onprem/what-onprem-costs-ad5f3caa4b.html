What on-prem actually costs

Three ways to give an enterprise its own git2docs: a dedicated instance we operate, or a self-managed install in their AWS account reaching Claude through the hosted API or through Bedrock. Here is the monthly bill for each, and what it takes to stand one up.

Standing one up

Two paths, and the prerequisites differ far more than the price does. Lead with the first one: most customers who say “on-prem” want their own database and their own region, not their own cluster. Neither path is shippable today — the difference is that one is days of engineering away and the other is months.

Path one — the managed stack, no cluster

Days of engineering away

The stack production already runs on: one Vercel project, one Neon project in the region they name, one Render service. Nothing is installed in the customer's environment, so there is no cluster, no IAM role and no questionnaire about their perimeter. It comes in two variants, and the only difference is whose accounts hold the three projects — which happens to be the difference procurement cares about.

Variant A — we operate it

The projects live in our accounts. They get their own database, their own region and no operational burden; we run migrations, upgrades and backups on our cadence, and carry the pager.

Procurement: we remain a processor, and so do Vercel, Neon, Render and Anthropic — all under our contracts. Good enough for an isolation or residency question; not an answer to a third-party-processing one.

Drift: none. Every instance is current because we upgrade it.

Variant B — they operate it

The same three projects, created in the customer's own Vercel, Neon and Render accounts, with their own model credentials. Their billing, their contracts, their change control.

Procurement: this is the strong one. Those vendors become theirs under their own DPAs, and we stop being a processor at all — we are a software vendor. It also answers “our infrastructure” for every enterprise that means their accounts rather than their VPC.

Drift: it returns. They run the version they last upgraded to, and support becomes advisory because we cannot see the instance.

Both variants need the same thing from the customer: a GitHub App approval on their org — the one enterprise gate that never goes away — plus the region their policy requires, a DNS name if they want their own, and an identity provider if they want SSO.

How variant B ships: a deploy skill over declarative config

We already distribute agent guidance as a Claude Code plugin, so the customer's own Claude Code is the natural operator here — the same pattern as the validation loop. One correction to the obvious version of this idea: the skill should not be the installer. Three vendor APIs driven conversationally with someone else's credentials fails in ways nobody can see, and “the agent half-created my Neon project” is an unanswerable support ticket.

Ship declarative provisioning underneath it — all three vendors have Terraform providers, so the whole instance is roughly fifteen resources — and let the skill do what a runbook cannot: preflight the prerequisites, drive the apply, verify the worker booted and the migration ledger advanced, apply version upgrades, and diagnose a sick instance from the outside. That keeps the failure modes idempotent and inspectable, and it still turns weeks of install documentation into a plugin version bump.

Path two — a self-managed install

Specified, not yet built

For the customer who genuinely needs it inside their perimeter and under their change control. The chart below is the shape agreed in the engineering spec, not a published artifact — treat it as what an install will look like, and do not promise a delivery date from this page.

Bedrock is not the cheaper option, and selling it as one will go wrong at renewal. Per token it costs the same or slightly more, plus about $15–22 a month for the private endpoint. What the customer buys is the data boundary, one invoice, and no API key sitting in their cluster. For a security review, that is usually worth more than the difference.

Who is asking, and what answers them

“Source can't leave our network”

No product to sell. Comprehension and synthesis run on Claude; that is the product, not a configuration flag. Disqualify on the first call rather than at the demo.

“No third party may hold our data”

Bedrock in their own account, hosted control plane. Days of engineering, no chart, no release tax. Satisfies more procurement reviews than it sounds like it should — lead with it.

“Not a database shared with your other customers”

A dedicated instance, in the region they name — which also answers EU residency, their own retention policy and their own maintenance window. This is the row most enterprises are actually in while using the vocabulary of the next one. Days of engineering, and we keep operating it.

“It runs on our infrastructure”

The full install: Helm chart, their EKS, their RDS, their change control. Weeks to build, and a permanent cost on every release after that. Price it accordingly.

Say this part out loud

Self-managing costs several times the hosted subscription, before anyone writes a page. On-prem is a control purchase, not a savings purchase.

  • A dedicated instance is not row two. Vercel, Neon, Render and Anthropic all remain processors, and all remain in our accounts. Procurement counts processors, not instances — so do not offer it against a question about third-party processing.
  • Documentation text still reaches Voyage for embeddings, on every option including Bedrock. Voyage also publishes model packages on AWS Marketplace that run in the customer's own VPC — confirm the model and its output dimension before offering that as a closed loop.
  • Someone has to operate it. These are platform invoices only. On the self-managed option that operator is the customer's platform engineer, and their time is the larger cost.
  • Versions drift, but only on one option. A self-managed customer runs whatever they last upgraded to and will report bugs fixed months ago. A dedicated instance never drifts, because we upgrade it. That, not cost, is the strongest argument for the middle rung.
  • N instances is somebody's job. Three dedicated instances by hand is fine; twelve is not. The fan-out has to be automated from the first customer rather than the fourth.
  • The deploy skill holds real credentials. Vercel, Neon, Render and a model key in one agent session is a wide blast radius. That is an argument for declarative provisioning the customer can read before applying, and against a skill that improvises against three APIs.

AWS figures are list prices for us-east-1, on demand, retrieved November 2026 — verify in the AWS Pricing Calculator before quoting. EKS $0.10/cluster-hour, NAT gateway $0.045/hour plus data, ALB $16.20/month plus LCUs, public IPv4 $3.65/month, RDS db.m7g.large PostgreSQL about $0.168/hour. Dedicated-instance figures use Neon at about $0.106 per compute-unit-hour plus $0.35/GB-month of storage, and Render worker plans at $25 / $85 / $175. Note that the worker polls the database every ten seconds, so serverless scale-to-zero never happens and the database is billed as continuously awake. Model prices are Claude Sonnet 4.6 at $3.00 / $15.00 per million tokens, cache reads at $0.30. Token volume per page is an internal working assumption — 45,000 input and 10,000 output — and should be recalibrated from a real customer run before it appears in a quote. Reserved instances, Savings Plans and an AWS enterprise discount all reduce the self-managed column materially.
